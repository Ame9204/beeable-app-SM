BEEABLE - PRE-DEMO CHECKLIST
============================
Tick each box on the day. Times are relative to when the demo starts.


1. THE DAY BEFORE
-----------------
[ ] Build the latest APK and install it on the demo phone (and on a backup phone).
      cd frontend && npm run build:android
      then build with Gradle. If gradlew complains about "-classpath", set
      JAVA_HOME=C:\Program Files\Android\Android Studio\jbr first.
      APK: frontend/android/app/build/outputs/apk/debug/app-debug.apk
[ ] Uninstall the old app first (or clear its storage) so the welcome screen shows
    on first launch.
[ ] Push the latest backend to GitHub so Render redeploys it, then open
    https://beeable-api.onrender.com/health and check:
      - "ok": true
      - "graph_edges" is about 307
      - "intake" -> "provider": "gemini", "key_set": true, "last_error": null
[ ] Set up the cached AI demo photo. It is MISSING right now: data/processed/ has no
    demo_photo.jpg or demo_intake.json. Without them, the report step has no backup
    if Gemini is slow or down.
      - Put the exact photo you will report in data/processed/demo_photo.jpg
      - Save a good AI response for it in data/processed/demo_intake.json
      - Commit both. The photo you pick on the phone must be byte-for-byte the same file
        (copy it to the phone's gallery; don't take a new photo during the demo).
[ ] Rehearse the full demo story (section 4) twice from start to finish, on the phone.
[ ] Charge both phones and the laptop. Bring a charger and a USB cable.


2. ON THE DAY: 30 MINUTES BEFORE
--------------------------------
[ ] WAKE RENDER UP. The free tier sleeps after about 15 minutes idle, and the first
    request then takes about 1 minute. Open /health in a browser, and open it again
    every ~10 minutes until the demo starts.
[ ] Render wipes its data on every restart or redeploy. This is expected (we have no
    database). Reports made before a restart are gone and the seeded sample reports
    come back. Do NOT redeploy after rehearsing; if you do, re-check the data.
[ ] Check the internet connection the phone and laptop will use (venue Wi-Fi or a
    hotspot). Have a mobile hotspot ready as a backup.
[ ] Turn on GPS/location on the phone. Grant BeeAble location and camera permission
    BEFORE going on stage, so no permission pop-ups appear during the demo.
[ ] Remember that off campus (more than 700 m from the centre) the route starts from
    the campus centre. That's fine for a demo away from UiTM, but expect it.
[ ] Turn on Do Not Disturb on the phone. Set brightness to max. Turn off auto-lock
    or set it to a long timeout.
[ ] If you mirror the phone screen (scrcpy / casting), test it on the venue projector.


3. STAFF DASHBOARD (/insights) ON THE LAPTOP
--------------------------------------------
[ ] The API only accepts the dashboard from http://localhost:5173 (CORS_ORIGINS in
    render.yaml). Run the dashboard locally on exactly that port:
      cd frontend && npm run dev
    If Vite moves to port 5174 because 5173 is busy, close the other dev server first.
    Otherwise the dashboard falls back to sample data and resolving won't reach the phone.
[ ] Make sure frontend/.env (or the shell) points VITE_API_URL at
    https://beeable-api.onrender.com, the SAME backend the phone uses.
[ ] Open http://localhost:5173/insights and check that the yellow "sample data" banner
    is NOT showing. If it is, the API is unreachable or asleep.
[ ] Zoom the browser so it can be read from the back of the room.


4. DEMO STORY: QUICK CHECK RIGHT BEFORE GOING ON
-------------------------------------------------
[ ] 0. (Optional opener) Fresh install -> Welcome -> Create account -> profile setup
       (language, Step-free) -> lands on Navigate. Or pre-do this so the demo starts
       on the map.
[ ] 1. Step-free, destination Unit Kesihatan (clinic): the shortest route has steps,
       the BeeAble route avoids them; open "Why this route?".
[ ] 2. Switch to Easy walking: the route changes on the same data.
[ ] 3. Report tab: the demo photo + BM text or voice -> AI ticket in about 2 s ->
       shows as Unverified.
[ ] 4. Laptop /insights: Verify the new report -> it appears in the priority list
       with its score breakdown.
[ ] 5. Mark it Resolved -> on the phone, reload the route -> the route updates.

    No sample-data banner should appear on the phone at any point. If it does, the
    phone can't reach the API: check the internet, then /health.


5. WHAT TO SAY (DATA HONESTY - DON'T SLIP)
------------------------------------------
[ ] Say "no known barriers for your profile", never "accessible route".
[ ] Point out the surveyed share and the dashed (unknown) segments.
[ ] The AI ticket is a SUGGESTION; staff verify it. Never imply the AI verifies.
[ ] Any simulated data in the dashboard is labelled "simulated". Say so if asked.
[ ] Accounts live on the phone only; reports are anonymous (reference number).
[ ] The campus is the PILOT; the target is an SDP township precinct.
[ ] No MS 1184 compliance claims.


6. IF SOMETHING BREAKS ON STAGE
-------------------------------
- API asleep or down: the app shows sample data with a banner. Say "this is the
  offline fallback", keep going with the story, and mention the live version.
- Gemini slow or failing: use the cached demo photo (section 1) so the ticket still
  appears. If the AI fails, the report is still saved (the AI source shows as
  "fallback") and staff can set the category on /insights. Rehearse this once.
- Phone dies or the app crashes: switch to the backup phone (APK already installed,
  permissions already granted).
- Keep a screen recording of a full successful run on the laptop as a last resort.
